# Architecture & Known Limitations

## Architecture Overview

**Stack:** React + TypeScript (frontend) → Express + TypeScript REST API (backend) → PostgreSQL (via Prisma ORM).

```
┌─────────────────┐        HTTPS/JSON        ┌──────────────────┐       SQL        ┌──────────────┐
│  React frontend  │  ────────────────────►   │  Express backend  │  ───────────►    │  PostgreSQL   │
│  (Vercel)        │  ◄────────────────────   │  (Render)          │  ◄───────────    │  (Render)     │
└─────────────────┘        JWT in header       └──────────────────┘                  └──────────────┘
```

- **Auth**: JWT-based. On login, the backend signs a token containing `userId` and `role`. The frontend stores it in `localStorage` and attaches it as `Authorization: Bearer <token>` on every request via an Axios interceptor.
- **Authorization**: role checks happen in Express middleware (`requireRole(...)`), not in the frontend — the frontend hides buttons a role can't use, but the backend is the actual enforcement point. This matters because a UI-only restriction can be bypassed by calling the API directly (e.g. via Postman); the backend check is what actually protects the data.
- **Data model**: Prisma schema defines Users, Customers, FollowUps, Products, StockMovements, Challans, and ChallanItems. Money fields use `Decimal`, not `Float`, to avoid floating-point rounding errors.
- **Challan business logic**: creating/confirming a challan runs inside a single Prisma `$transaction` — the stock check, the stock decrement, and the stock-movement log entry either all succeed together or all roll back together. This prevents a scenario where stock is deducted but the movement log isn't written (or vice versa) if something fails mid-way.
- **Product snapshotting**: each `ChallanItem` stores its own copy of the product's name, SKU, and price at the time of sale, rather than only a foreign key to the product. This means editing a product's price later doesn't retroactively change historical challans — same principle as a paper invoice: it reflects what was true when it was issued.

## Known Limitations

- **Open registration endpoint**: `POST /auth/register` doesn't require an existing Admin to create a new user. This was left open intentionally to make seeding test accounts easy during development, but in a real production system this should be gated so only Admins can create new logins.
- **Challan number generation**: generated by counting existing challans (`CH-2026-000123`). This is fine at this project's scale, but under concurrent writes two challans could theoretically be created in the same instant with a raw counting approach; a production system would use a database sequence instead.
- **No PDF invoice export, S3 image upload, or Docker/CI setup** — these were listed as bonus items in the brief and were deprioritized in favor of finishing the core required modules within the deadline.
- **Mobile responsiveness untested** — the layout uses a fixed sidebar that hasn't been verified below tablet width.
- **Follow-up date** is stored per customer but there's no automated reminder/notification when a follow-up is due — it's just a field you can view and set.

## Assumptions Made

- "Sales Challan" quantities/prices don't include tax (GST) calculations — the customer record stores a GST number for reference, but no invoice/tax computation logic was built, since the brief's required fields didn't specify a tax model.
- Stock movements created automatically by challan confirm/cancel are attributed to whichever user performed that action, not to a separate "system" user.
- All 4 roles can view Customers and Products; only Admin/Sales can create or confirm/cancel Challans; only Admin/Warehouse can create/edit Products and record stock movements — this split was inferred from the spec's description of each team's job, since the document didn't give an explicit permission matrix.
